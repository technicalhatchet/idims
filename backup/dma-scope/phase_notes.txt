## Recommended Phase 2: make it useful on-site

The biggest gap right now isn't smarter AI — it's **context**. DMA lives on its own page. When you're standing in front of a Whirlpool with F9E1, you want memory *on the work order*, not a separate detour.

Phase 2 should focus on **"similar past repairs, right where I'm diagnosing."**

Roughly:

1. **In-context panel on the WO** (mobile first)
   - On open, query DMA by current equipment make/model/subtype + any error code from notes/symptoms
   - Show 3–5 past confirmed fixes with links back to those WOs
   - Optional "copy fix language into note" shortcut

2. **Repair tags (manual first)**
   - Tags like `drain`, `compressor`, `control_board`, `pressure_hose`
   - Many-to-many: `work_order_tags` / `tags`
   - Add to Repair Outcome form + filter on Repair Memory search
   - Sets you up for extraction later without needing it now

3. **Error code reference table (lightweight)**
   - `error_codes`: manufacturer, appliance type, code, description
   - Searchable lookup UI
   - Link from a code → all matching repair outcomes in your history
   - You can seed it slowly (Whirlpool/Samsung codes you hit often)

4. **Capture habit / data quality**
   - Nudge Repair Outcome when marking repair **Completed** or **Completed — Pending Payment**
   - Maybe a "missing outcome" indicator on closed WOs
   - Backfill a few recent successful jobs so search isn't empty

That's still additive architecture: new tables, new endpoints, new UI panels — no rework of work orders.

---

## Phase 3: extraction (still no LLM required)

Once search + tags are in daily use:

- On note save, run simple Python rules:
  - Regex for error codes (`F9E1`, `E01`, etc.)
  - Keyword scan for components (`drain pump`, `compressor`, `thermistor`)
  - **Suggest** tags — don't auto-commit
- Optional background job later if sync processing gets slow

This is where the backend starts feeling more "intelligence layer" than CRUD, but you can fake v1 synchronously on note save.

---

## Phase 4: statistical memory

When you have enough rows:

- "Top fixes for this error code on this brand"
- "Success rate when part X was replaced"
- Callback patterns

Useful for you solo, but it needs volume. Don't build this until you have ~20–30+ outcomes with decent tagging.

---

## Phase 5+: semantic search / AI assist

Only after structured search feels insufficient:

- Embeddings on `confirmed_fix` + complaint + summary
- pgvector in Supabase
- "Find repairs similar to this symptom paragraph"

Powerful, but it's the wrong next move if Phase 2 isn't done — you'll search an empty or thin corpus with fancy tools.

If I were sequencing for **solo field use**:

| Priority | What | Why |
|----------|------|-----|
| 1 | In-context "similar repairs" on WO mobile | Biggest daily payoff |

=== LINE 3551 ===
You're thinking about it the right way. Intake + view is the core, but a few supporting pieces make it actually usable day to day.

## The problem with today's DMA

`dma_repair_outcomes` is **1:1 with work orders**. Equipment context comes from the WO join; search results link to `/work_orders/{id}`. That fits Atomic Repair jobs, not employer field notes with no client and no order.

You want a **second lane** in the same repair memory system: same kind of knowledge, zero WO/client/billing baggage.

---

## What you're building (conceptually)

Think of it as **Repair Memory Records** — standalone entries that only hold technical repair knowledge.

```
Repair Memory (search)
    ├── From Atomic work orders (existing — Repair Outcome notes)
    └── Standalone records (new — manual intake, CSV later)
```

No fake order numbers. No clients. Internal ID only (e.g. a UUID or simple `RM-042` display label if you want something human-readable).

---

## V1 scope: yes, intake + view — plus a few essentials

### 1. Intake form (required)
Same fields you already use on Repair Outcome, plus **equipment on the record itself** (since there's no WO):

| Field | Notes |
|--------|--------|
| Equipment make / model / type / subtype | Required-ish (at least make or subtype) |
| Customer complaint / symptoms | Free text — technical only, no names |
| Error code | |
| Problem code / resolution code | Same dropdowns as today |
| Confirmed fix | Required |
| Replaced parts | Free text |
| Repair successful / callback required | Checkboxes |
| Technician summary / notes | Optional |
| **Date performed** | Optional but useful for FT jobs logged later |

Explicitly **not** on the form: name, phone, email, address, employer WO#, payment.

### 2. Detail view (required)
A **dedicated page** beats a modal as the primary view — easier on mobile, bookmarkable, room to edit.

`/techdashboard/dma/records/[id]` — stripped-down read view:
- Equipment block
- Symptom / error code
- Fix + parts + codes
- Success flags
- When recorded / when performed
- Edit + Delete buttons

Search results can open this page instead of a work order when the record is standalone.

A **modal** is still nice for a quick peek from search without navigation — optional polish, not required for V1.

### 3. Unified search (required)
Your existing Repair Memory search should return **both**:
- WO-linked outcomes (link → work order notes tab)
- Standalone records (link → detail page)

Each result gets a small badge: **Atomic job** vs **Field record** (or similar).

Without this, standalone data is orphaned.

### 4. Edit + delete (required for you solo)
You'll typo "Whirlpool" or paste the wrong error code. Simple edit on the detail page; delete with confirmation.

### 5. "Add record" entry point (required)
On `/techdashboard/dma`:
- **+ Add field record** button → intake form (page or sheet)
- Empty state text updated: "Add a field record or a Repair Outcome on a work order"

---

## What you do **not** need for V1

- Work orders, clients, appointments, billing, Stripe
- Addresses or order numbering schemes
- CSV import (Phase 2 — design the form fields to match the CSV columns you'll import later)
- Tags (Phase 2/3)
- Linking a standalone record to a WO later (nice later, not now)
- Separate app or duplicate auth

---

## Backend shape (when you build it)

**New table** — e.g. `dma_repair_records` — not nullable `work_order_id` on the existing table.

Reasons:
- Clear compliance story: "these rows never had a customer"
- WO delete doesn't wipe your training corpus
- Simpler permissions and reporting

**Search** — one service that queries both sources and normalizes the response shape (equipment, fix, codes, `source_type`, `detail_url`).

**CSV later** — same columns as the form; bulk POST or import endpoint.

## Compliance angle (why this is cleaner)

Standalone records with **no PII fields in the schema** are easier to reason about than anonymized WOs. You're not storing customer data and redacting it — you're storing **only** what DMA needs. If policy ever asks, you can say: field memory is technical repair metadata with no customer identifiers.

Still worth checking employer policy on **using de-identified repair knowledge** from their jobs — but you're not mirroring their CRM.
